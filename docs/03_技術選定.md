# 言語・実行環境・データベースの選び方 v0.1

これは比較資料と推奨案です。本番方式は企画責任者の決定待ちです。料金契約・外部データ送信・ストア申請は実行していません。

## 混同しやすい言葉

|名称|何か|このアプリでの役割|
|---|---|---|
|Java|プログラミング言語|サーバーの処理を書く選択肢。Androidにも利用される|
|JavaScript|Javaとは別の言語|ブラウザの画面や操作を動かす。今回の試作で使用|
|TypeScript|JavaScriptに値の種類のチェックを加える言語|実装が大きくなるとデータの取り違えを検出しやすい|
|Node.js|JavaScriptをブラウザの外で動かす実行環境|サーバーの起動等に使う。言語ではない|
|Python|プログラミング言語|Webサーバー、分析、自動化などに利用できる|
|Spring Boot|JavaでWebサーバーを作るための土台|入力検証・DB接続・認証などを構成する|
|SQL|データを保存・検索するための言語|例：ToDoの一覧を取り出す|
|MySQL / MariaDB / PostgreSQL|データベース製品|保存場所を管理する仕組み。SQLで操作する|
|SQLite|端末内のファイル型データベース|アプリ内保存に使える。常時稼働するDBサーバーが不要|

「自動化がないからPythonよりJava」は決定的な基準ではありません。Pythonでもこのアプリは作れます。大切なのは、スマホでどう配るか、端末間で共有するか、どんな技術を学びたいか、運用できるかです。

## 言語の比較

|候補|利点|負担・注意|適する条件|
|---|---|---|---|
|Java + Spring Boot|業務システムで説明しやすい構成。型チェックがあり、既存企画に一致|画面側には別途JavaScript等が必要。小規模でも構成が増える|Javaの学習・サーバー開発経験を重視し、クラウド同期が必要|
|TypeScript + Node.js|画面とサーバーで同系統の言語を使える。変更を揃えやすい|ライブラリ選定、依存更新、認証・運用設計が必要|開発範囲を絞りながら画面とサーバーを一緒に保守したい|
|Python + Django等|データ分析へ広げやすい。管理機能を作りやすい|画面は別言語。モバイルの端末機能は別途対応|分析を重視し、Pythonの経験がある|
|TypeScript + React Native / Expo|iOS・Androidで多くのコードを共有できる。端末内SQLiteと組み合わせられる|ビルド・端末テスト・ストア設定が必要。Web試作の画面をそのまま使うわけではない|両ストアが主目的で、端末内利用から始めたい|
|Dart + Flutter|両スマホOSを共有実装しやすい|Dartを学ぶ。Web画面からの移行時に作り直しが必要|スマホ専用の見た目・操作を統一したい|

## データベースの比較

|候補|向く用途|考慮点|
|---|---|---|
|SQLite|利用者ごとに端末内保存、オフライン優先|端末間同期は別途設計。機種変更・バックアップ・暗号化の方針が必要|
|MySQL|JavaまたはNode.jsのサーバーと組み合わせる一般的な構成|DBとAPIサーバーの運用、利用者分離、バックアップ、費用が増える|
|MariaDB|MySQL系の知識を使えるサーバーDB|MySQLと完全同一ではない。使う版とSQLの互換性を検証する必要|
|PostgreSQL|制約を使い厳密にデータを管理するサーバー構成|今回の規模でMySQLより必ず優れるわけではない。運用は必要|
|localStorage|導入不要の小さなブラウザ試作|SQLではない。同期・復元・容量・同時書込に制限。本番の推奨DBではない|

スマホアプリからMySQLへ直接接続しません。サーバーの窓口（API）を通し、本人確認と利用者ごとのアクセス制御を行います。DBのパスワードをアプリに埋め込まないためです。

## 現時点の推奨案

まずスマホの利用形態を決めることを推奨します。

**両ストア向け、同期なしで開始するなら：TypeScript + React Native/Expo + SQLiteを第一候補。** 初期利用者2名の時間の振り返りを、アカウント登録なしで試せるためです。サーバー運用を減らせます。一方、機種変更・バックアップ・OSによる中断を実機で設計検証する必要があります。

**複数端末の同期とJavaの経験を優先するなら：Java + Spring Boot + MySQLを第一候補。** 企画書の予定と一致します。画面はJavaScript/TypeScript、スマホへの配布方式は別途決めます。費用と運用範囲は増えます。Node.js構成でも同じ機能を実現できます。

アプリの規模だけではMySQLとMariaDBの性能差は選定理由になりません。既存企画、学習資料、利用するホスティング環境との相性ならMySQLを比較の基準にするのが自然です。特定クラウドや有料サービスはまだ選びません。

## 今回、実際に書いたもの

- 画面・計測・集計：JavaScript。ブラウザだけで操作案を確認できるため。TypeScriptやReact Nativeへの本採用を意味しない。
- ローカル配信：Node.js標準機能。npm追加依存なし。Node.js 24.19.0で技術検証。
- データ保存：localStorage。外部送信・費用・DB作成が不要な試作に限定。
- テスト：JavaScript（Node.js標準テスト）とPython（Playwrightでブラウザ操作）。Pythonはテストの道具として使用。
- DB設計：SQLite端末内案を基本とし、MySQLサーバー案への変更点を別記。DBサーバーは作成していない。

今回のJavaScript試作は、要件・操作を確認するための小さな作業です。本番方式の選択前にJavaから恒久的に変更したものではありません。移植時に画面実装の変更が必要になることも明記しておきます。
